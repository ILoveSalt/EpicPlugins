# Техническое задание на игровой движок «HGDS Engine» и встроенный редактор

**Версия:** 1.0
**Период разработки:** 16.09.2026 — 17.11.2026
**Платформа:** Windows x64 (целевые: Windows/Linux)
**Состав:** ядро движка (`hgdsEngine.Core`), редактор (`hgdsEngine.Editor`), игра (`HGDS_Breachpoint.Game`), инструменты (`tools/`), документация

---

## 1. Общие сведения

**1.1. Назначение.** Разработка собственного игрового движка и встроенного редактора для кооперативного шутера с **разрушаемым воксельным миром**. Движок обеспечивает цикл кадра, подсистемы рендера, ECS, физику/коллизии, сетевой обмен, ассеты и инструменты разработки; редактор — вьюпорт реального времени, редактирование мира, иерархию объектов, инспектор и управление сценой.

**1.2. Область применения.** Игровой проект «HGDS: Breachpoint» (кооп, вид от первого лица, воксельный террейн с разрушением), а также как самостоятельный инструментарий для сборки уровней и прототипирования 3D-сцен.

**1.3. Принципы архитектуры.**
- Строгое разделение слоёв: `Core` (движок) → `Editor`/`Game` (потребители). **Core не зависит ни от кого**; прямые связи Editor ↔ Game запрещены.
- Игровой код и скрипты не видят конкретных библиотек оконного/графического/сетевого уровня — только собственные интерфейсы (`IWindowService`, `IInputService`, `INetworkServer` и т. д.).
- Нулевые аллокации в горячих путях (кадр, рендер, сеть, логирование).
- Модульность графической подсистемы: смена графического API без переписывания игровой логики.

---

## 2. Цели разработки

**2.1. Функциональные цели.**
1. Редактор уровней с вьюпортом реального времени и полноценной работой с воксельным миром (кисть, материал, разрушение).
2. Рантайм-ядро: цикл кадра, DI-контейнер, логирование, окно/ввод, ECS, ассеты, сеть.
3. Воксельная подсистема: чанковое хранение, генерация мешей, трассировка лучей, коллизии, загрузка/сохранение.
4. Персистентность сцен: собственный формат, поиск уровней, быстрое сохранение/загрузка.
5. Подготовка к релизу: защита чувствительного состояния (данные камеры/игрока), упаковка и шифрование ресурсов при экспорте, статическая сборка рантайма.

**2.2. Технические цели.**
- Кадр ≤ 16.6 мс при воксельной сцене среднего размера (цель), отсутствие видимых артефактов (швы чанков, «бегущие» полосы по граням).
- 0 ошибок компиляции и 0 предупреждений собственного кода на каждой фиксируемой сборке.
- Все подсистемы заменяемы: графика, окно, ввод, сеть, сериализация.

**2.3. Ограничения.**
- Срок — 16.09.2026 – 17.11.2026 (по этапам, см. раздел 5).
- Разработка в одиночку; проверка сборки и запуска — вручную, с фиксацией результата в журнале прогресса.

## 4. Из чего сделан (состав и технологии)

### 4.1. Технологический стек

| Слой | Состав |
|---|---|
| Языки | **C# / .NET 10** — редактор, инструменты и игровая логика · **C++** — нативное ядро и расширения · **HLSL** — шейдеры · **Python** — сборочные скрипты |
| Графика | **DirectX 11** (текущий рендер), **Vulkan** и **Direct3D 12** (задел/цель). Собственные абстракции: устройство, цепочка отображения, буферы, конвейеры, цели рендера, компилятор шейдеров |
| Интерфейс редактора | **ImGui.NET** (докинг-панели) + **ImGuizmo** (манипуляторы), собственная отрисовка служебных элементов (сетка, оверлеи) |
| Математика | **System.Numerics** — векторы, матрицы, кватернионы, фрустум |
| Импорт ресурсов | **AssimpNet** (3D-модели) → внутренние структуры → собственный формат меша |
| Сеть | **LiteNetLib** (транспорт) + собственный слой пакетов, ролей и конфигурации |
| Сборка | .NET SDK 10 / MSBuild, нативная сборка через CMake и скрипты, Git |
| Отладка и контроль качества | Собственный zero-alloc логгер, обратное чтение цели рендера, автотест ядра (`--selftest`), журнал прогресса |

### 4.2. Слои решения

| Слой | Содержимое |
|---|---|
| `hgdsEngine.Editor` | Оболочка, панели, инспектор свойств, редакторы сцены/анимации/шейдеров/скриптов, импортёры, сборка и экспорт, отладчик, темы, расширения |
| `hgdsEngine.Core/Foundation` | База: объектная модель, контейнер значений, математика, ввод-вывод, шифрование, настройки, нативный C-интерфейс |
| `hgdsEngine.Core/Scene` | Сценная система: узлы 3D, UI-тулкит, анимация, аудио, ресурсы, темы, цикл мира |
| `hgdsEngine.Core/Services` | Подсистемы: рендер, физика, аудио, текст, камеры, дисплей, навигация, захват кадров |
| `hgdsEngine.Core/Backends` | Драйверы: Direct3D12, Vulkan, OpenGL, Metal, окна, платформы, аудио, кодеки |
| `hgdsEngine.Core/Platforms` | Платформенные слои: Windows, Linux |
| `hgdsEngine.Core/Modules` | Встроенные модули (≈60): текстуры, медиа, импорт, инструменты сцены, физика, скрипты, шейдеры, сеть, **воксельная подсистема** |
| `hgdsEngine.Core/External` | Сторонние библиотеки: графика, шрифты, физика, сеть, медиа, сжатие |
| `hgdsEngine.Runtime` | Рантайм: точка входа, главный цикл, режимы (игра / редактор / сервер), выход |

| `tools` | Диагностика, утилиты, мониторы сборок |

Направление зависимостей: `Editor → Core`, `Game → Core`. **Core не зависит ни от кого**; прямые связи Editor ↔ Game запрещены; игровой код видит только интерфейсы ядра. Ядро собирается как нативный модуль, редактор и инструменты — на C#/.NET.

### 8.7. Сборочная система, шаблоны и ресурсы

| Структура | Назначение |
|---|---|
| `Build/` | Сборочная система и подготовка зависимостей |
| `Build/Configurations/` | Профили сборки: Debug / Release / Профайл / Выделенный сервер |
| `Build/Scripts/` | Генерация версии, сборка зависимостей, валидация API, упаковка пакетов |
| `Build/Templates/` | Шаблоны проектов и шаблоны экспорта под целевые платформы |
| `Build/Presets/` | Пресеты экспорта: платформы, фильтры ресурсов, выборочное шифрование, подпись |
| `Build/Dependencies/` | Получение и подготовка сторонних зависимостей |

- **Ядро** собирается нативным компилятором (MSVC / Clang) со сборочными скриптами; **редактор и игра** — средствами .NET SDK.
- Целевые платформы и графические API задаются параметрами сборки: одна и та же кодовая база даёт сборки под Windows/Linux и под разные графические API.
- **Шаблоны экспорта** собираются отдельными целями; без них невозможна публикация игры (и, соответственно, включение шифрования ресурсов).
- Ресурсы проекта: метаданные импорта хранятся рядом с исходными файлами, кэш импорта — в служебном каталоге проекта.
